# Guardrails instead of comments

> **Rules are enforced by machines, not by comments.** Instead of explaining a rule in a comment, make breaking it fail the compiler, a lint, a test or a hook. The failure message tells the reader how to fix the root cause.
>
> The strict form, **no code comments at all**, is a MonkeyMode default you can switch per guardrail profile (`"noComments": true|false` in `guardrails/*.json`). The rest of this doc applies either way.

## Rules

- When `noComments` is on for a profile, files in its scope contain no comments (`//`, `/* */`, `///` for C-style languages). Generated files and third-party packages are excluded.
- When you feel the urge to "write down why", **fix the cause instead**:
  1. Make it visible through names and structure (extract methods, rename, enums, value types).
  2. Encode the constraint in code (table below).
  3. If it is a rule, add it to the guardrails.
  4. If it is a decision record, write it in `docs/`, not in the code.
- When a guardrail fires, **never get past it by editing rule files, adding allowlist entries or bypassing hooks (`--no-verify`).** If the rule looks wrong, stop and ask the user, with your reasoning. Changes to `guardrails/`, `.githooks/` and agent hook settings need user approval.

## What enforces what

| Want to keep | Mechanism | On violation |
|---|---|---|
| No comments | `tools/guardrails/check.py` (ignores `//` inside string and char literals) | Prints line number and how to respond |
| Banned APIs and patterns | Engine profile `guardrails/<engine>.json` ([list](13_BANNED_APIS.md)) | Prints rule ID, why, and what to use instead |
| No secrets in the repo | Core profile `guardrails/secrets.json` | Prints the rule and where to put the value instead |
| Module dependency direction | The engine's module system (assemblies, crates, modules, plugins) plus the adapter's rule check | Prints the forbidden pair and how to invert it |
| Editor code never ships in runtime | Editor-only modules/targets | Build fails |
| Limit outside access | Visibility (`internal`/`private`/`pub(crate)`), sealed types, module boundaries | Build fails |
| Required components, no duplicates | Engine attributes (`[RequireComponent]`, `@tool` checks, `meta=(...)`, Bevy required components) | The editor enforces it |
| Deprecation and replacement | Deprecation attributes with an error and a "use X instead" message | Compile error shows the message |
| Inspector/property value ranges | Validation hooks or data-asset validation tests | Editor or test failure |
| Game rules (reset after failure, server validation) | Unit tests whose names document the rule (`Challenge_AfterFailure_ResetsToInitialState`) | Test failure |
| Network contracts | Multi-client play tests ([network authority](04_NETWORK_AUTHORITY_AND_TESTING.md)) | Test failure |

## Writing guardrail messages

A guardrail message must make the next agent fix the cause, not work around it.

1. What is banned (one sentence)
2. Why (the real problem it causes)
3. What to use instead (a concrete alternative)
4. The source doc

Bad: `Find is banned`. Good: `Scene-wide lookups are banned. They create hidden dependencies on hierarchy shape and load order and break at network spawn time. Use serialized references, injection at creation, or a registration-based registry.`

## Adding a guardrail

- A mistake that happens twice is a candidate. Propose it in the completion report's "follow-ups / guardrail proposals" ([response style](06_RESPONSE_STYLE_GUIDE.md)).
- Add it to `guardrails/` only after user approval. **Run one violating example and one passing example** for every rule.
- Rules a regex cannot catch precisely (for example "never send state through a one-shot RPC") belong in types, module rules or tests, not in a forced pattern.

## Profile format

Every `guardrails/*.json` file that has a `rules` array is a profile. `tools/guardrails/check.py` runs all of them.

```json
{
  "description": "What this profile is for",
  "scopeRoot": "src",
  "extensions": [".rs"],
  "noComments": false,
  "excludeDirs": ["target"],
  "skipFileSuffixes": [],
  "skipHeaderMarkers": ["<auto-generated"],
  "rules": [
    { "id": "BANNED_X", "pattern": "regex", "message": "what, why, instead, doc", "excludePaths": ["/tests/"] }
  ]
}
```

Patterns run on code with comments and string literals blanked out (C-style comment syntax). `excludePaths` entries are substrings matched against `/<relative path>`. A rule may also carry its own `extensions` list to apply to only some file types (for example headers only). Set `"stripLiterals": false` for profiles that must see string contents, such as the secrets profile.

## Known limits

- Regex checks can false-positive on a different symbol with the same name, and miss aliases and extension methods. Where the engine has a semantic analyzer (Roslyn banned-API analyzers, Clippy `disallowed_methods`, Unreal's UHT, GDScript warnings), use it as a second layer; the adapter docs say how.
- The comment detector understands C-style comments only. It does not detect `#` comments (GDScript, Python). Keep `noComments` off for those profiles.
- Interpolated strings with nested quotes can confuse the literal stripper.
- Tool files (`.ps1`, `.py`, `.json`) are not checked for comments, but new scripts should not need them either.
